# 브랜드 영상 재현·학습 (brand-video-recreate)

"이 영상처럼 멋지게"라고만 시키면 흉내만 나온다. 이 스킬은 그 대신 다섯 단계를 지킨다.

1. 참고 영상을 고르고 원본 화질로 받는다.
2. 숫자로 뜯는다.
3. 숫자대로 똑같이 만들며 학습한다. 원본과 나란히 놓고 제일 다른 곳부터 고친다.
4. 틀만 남기고 글·색·로고를 내 브랜드로 바꾼다.
5. 템플릿과 내용 파일로 나눠 저장해 다음에 글만 바꿔 쓴다.

핵심 규칙 세 가지.

- 눈으로 보고 "비슷하다"고 말하지 않는다. 비슷한지는 차이 숫자가 말한다.
- 숫자를 맞췄어도 화면에서 다르게 보이면 아직 틀린 것이다. 사람이 보는 것은 숫자가 아니라 화면이다.
- 참고 영상의 음악·화면은 연습할 때만 쓴다. 올리는 영상에는 한 프레임도 넣지 않는다.

도구는 `scripts/`에 있다. ffmpeg와 파이썬(numpy, Pillow)만 있으면 돈다. 스크립트마다 파일 맨 위 설명에 쓰는 법이 있다.

## 시작 전: 사용자에게 먼저 묻기

작업을 시작하기 전에 아래 질문을 하나씩 묻는다. 답을 받기 전에는 추측해서 채우지 않는다. 이 저장소와 `prompts/`에 나오는 「던스타」, 빨강 #CF1830, 던스타 로고, 캐릭터 민호는 예시다. 전부 사용자의 브랜드로 바꿔서 쓴다.

1. 브랜드(가게·회사·채널) 이름과 한 줄 소개는 무엇인가요?
2. 브랜드 대표 색(HEX 코드나 색 이름)과 쓰는 글꼴이 있나요?
3. 로고 파일이 있나요? 있으면 파일이나 경로를 주세요.
4. 영상을 어디에 올리나요? (유튜브, 인스타그램 릴스, 틱톡, 네이버 클립 등과 계정 이름)
5. 따라 만들고 싶은 잘 된 영상의 링크나 파일은 무엇인가요?
6. 영상에 넣을 말과 문구, 말투는 어떻게 할까요? (존댓말·반말, 짧게·길게)
7. 영상에 나올 캐릭터나 사람이 있나요? 있으면 그림이나 사진을 주세요.
8. 지금 쓸 수 있는 도구는 무엇인가요? (Claude Code, ffmpeg, Python 설치 여부)

답은 작업 폴더의 `measure/brand.md`에 그대로 적어 두고, 4단계(내 브랜드로 바꾸기)에서 이 파일만 보고 바꾼다. 단계마다 결과를 보여 주고 피드백을 받은 뒤 다음 단계로 넘어간다.

## 0. 작업 폴더

사용자가 영상 하나를 건네면 먼저 폴더를 만든다. 이름은 `<날짜>-<참고영상ID>-recreate/`.

```
ref/        원본 영상 (src.mp4), 원본 프레임 (frames/0001.png ...)
measure/    측정 결과: spec.md, 컷 json, 프레임별 csv, 접촉표
build/      재현 코드 (장면별 파일 하나씩)
out/        v1.mp4, v2.mp4 ... (판 번호를 올리며 저장, 덮어쓰지 않음)
qa/         나란히 영상, 차이 지도, 피드백 기록 (iteration_log.md)
```

`templates/spec.md`와 `templates/iteration_log.md`를 복사해 시작한다. 측정은 spec에, 판마다 받은 말과 고친 일은 log에 쓴다.

## 1단계. 참고 영상 고르기

할 일
- 사용자가 영상을 주지 않았으면 물어본다: 내 브랜드와 닮은 분위기, 길이 15~65초 안팎, 화면이 코드나 모션 그래픽으로 만들어졌는지 실사인지.
- 주어진 링크는 가능한 가장 높은 화질로 받는다(yt-dlp 같은 도구로 `-f bestvideo+bestaudio`). 이미 파일이면 `ffprobe`로 해상도·fps·길이를 적는다.
- 화질이 낮은 파일(480p 이하, 재인코딩된 캡처)이면 사용자에게 원본을 다시 구해 달라고 한다. 낮은 화질에서는 작은 움직임이 사라진다.

산출물
- `ref/src.mp4`, spec.md 맨 위에 출처(제작자 계정 + 게시물 ID), 해상도, fps, 길이, 프레임 수.

검수 기준
- 프레임 수 = 길이 x fps 와 맞는다(가변 fps 영상이면 `ffprobe -show_streams`로 확인).
- 이 영상을 고른 이유를 한 줄로 적었다("컷이 빠르다", "글자 효과가 좋다" 등). 이유가 없으면 학습할 대상이 불분명하다.

자주 틀리는 점
- 인스타 화면을 녹화한 파일을 원본으로 쓰기. 위아래 UI와 재인코딩 때문에 측정이 어긋난다.
- 소리 없는 영상이라도 오디오 스트림 유무를 적어 둔다. 효과음 시작점은 움직임의 박자다.

## 2단계. 숫자로 뜯기

할 일
1. 전 프레임을 뽑는다. 초당 몇 장이 아니라 **원본의 모든 프레임**이다.
   ```bash
   scripts/extract_frames.sh ref/src.mp4 ref/frames all png
   ```
2. 접촉표로 장면 경계와 움직임 장치를 찾는다. 처음에는 0.5초마다, 이상한 구간은 모든 프레임으로.
   ```bash
   python3 scripts/contact_sheet.py ref/frames measure/sheet_all.jpg --every 15 --cols 8
   python3 scripts/contact_sheet.py ref/frames measure/sheet_a.jpg --start 120 --end 175 --cols 8 --width 300
   ```
3. 컷 길이를 잰다.
   ```bash
   python3 scripts/cut_lengths.py ref/src.mp4 --json measure/cuts.json
   ```
   컷 수, 중간값, 평균, 분포가 나온다. 접촉표와 대조해 컷 경계가 맞는지 확인하고, 틀리면 `--thr`를 조정한다.
4. 반복 무늬(점무늬, 줄무늬)는 바탕만 있는 곳을 잘라 간격과 각도를 잰다.
   ```bash
   python3 scripts/dot_pitch.py ref/frames/0200.png --box 100,100,612,612
   ```
5. 움직이는 요소는 프레임마다 값을 표로 만든다. 글자가 뜨는 프레임, 물체의 위치·크기, 색이 차오르는 양, 어두워지는 정도를 쓴다.
   ```bash
   python3 scripts/region_series.py ref/src.mp4 --box 200,300,880,700 --color 207,24,48 --out measure/title_series.csv
   ```
6. 잰 것을 `measure/spec.md`의 표에 「측정」이라고 적는다. 추정은 「추정」이라고 구분해서 적는다.

잴 것의 목록(영상 종류별)
- 공통: 컷 길이 분포, 장면 경계 프레임, 배경색(픽셀 중앙값), 글꼴 크기·위치, 글자가 뜨는 프레임, 소리 시작점
- 반복 무늬: 간격(px), 각도(도), 점 크기, 어두운 곳과 밝은 곳에서 점이 어떻게 변하는지
- 물리 움직임: 생성 주기(프레임), 떠 있는 시간(초), 종단 속도(px/초), 서로 당기는지 여부
- 3D 같은 장치: 회전 각도, 카메라 이동 거리, 눌림 깊이와 시간
- 코드로 만든 영상이면 화면에 적힌 라벨이 구현 단서다("3,200 PARTICLES"가 있으면 점 3200개를 어떤 배치 공식으로 놓았는지 맞춰 본다)

산출물
- `measure/spec.md`(숫자 표), `cuts.json`, 접촉표 여러 장, 프레임별 csv.

검수 기준
- spec의 모든 숫자에 출처가 있다(어느 프레임, 어느 도구).
- 어떤 장면이든 "느낌"만 적힌 줄이 없다. 「옛날 느낌」은 간격 16px, 각도 30도, 컷 중간값 0.97초 같은 숫자로 바뀌어 있어야 한다.

자주 틀리는 점
- 1초에 4장만 뽑아 보고 만들기. 큐브가 돌아가는 장치처럼 0.1초 안에 일어나는 움직임을 통째로 놓친다. 13초 영상 391프레임을 전부 뽑은 뒤에야 큐브, 원통, 회전목마 장치가 보였다.
- 접촉표를 훑고 "구조는 같네"라고 판단하기. 접촉표는 구조를 찾는 용도다. 같은지는 4단계의 차이 지도로만 판정한다.
- 만든 사람이 쓴 도구를 짐작으로 정하기. AI 영상인지 코드 영상인지는 조용한 구간에서 앞뒤 프레임이 비트 단위로 같은지(정지 프레임), 표정이 바뀔 때 겹침이 없는지로 가려낸다. "입 모양이 매번 다르다"만 보고 단정하지 않는다.
- 비교 기준이 되는 프레임 색을 PNG 메타데이터(감마)가 틀어 놓는 경우가 있다. 차이가 이상하게 크면 두 쪽의 색 변환부터 확인한다.

## 3단계. 똑같이 만들며 학습

이 단계가 학습이다. 만들고, 원본과 나란히 놓고, 제일 다른 곳부터 고치고, 판 번호를 올린다.

할 일
1. 만들기 전에 도구를 정한다.

   | 장면 | 도구 |
   |---|---|
   | 글자·카드 UI·숫자·카메라 확대 | HTML + GSAP 또는 Remotion (프레임 번호만으로 그리는 결정적 렌더) |
   | 물리·입자·유리 같은 픽셀 단위 효과 | 파이썬 numpy 렌더러 또는 three.js 오프스크린 |
   | 진짜 물건의 빛·재질·원근 | 블렌더 스크립트 (빠른 EEVEE로 구조 검수, 마지막에 Cycles) |
   | 사진 위 질감(필름 입자, 망점) | 측정한 숫자로 합성 |

   랜덤과 시계는 쓰지 않는다. 어느 프레임을 뽑아도 같은 그림이 나와야 일부 구간만 다시 렌더할 수 있다.
2. spec의 숫자를 코드에 그대로 넣는다. 장면 하나를 한 파일로 만든다.
3. 1판을 렌더한다(`out/v1.mp4`). 원본과 같은 fps, 같은 해상도로 만든다.
4. 나란히 영상과 차이 지도를 만든다.
   ```bash
   scripts/side_by_side.sh ref/src.mp4 out/v1.mp4 qa/sbs_v1.mp4
   python3 scripts/diff_map.py ref/src.mp4 out/v1.mp4 --ranges 0-5,5-20 --heat-dir qa/heat_v1 --json qa/diff_v1.json
   ```
   평균 차이(0~255), 제일 다른 프레임, 제일 다른 구역이 나온다.
5. **제일 다른 곳부터** 고친다. 평균을 올리는 큰 틀림을 먼저, 작은 디테일은 그다음이다.
6. 판 번호를 올려 다시 렌더한다(v2, v3...). 판마다 `qa/iteration_log.md`에 적는다: 받은 피드백 원문, 측정해서 알아낸 원인, 고친 것, 차이 숫자.
7. 사용자의 피드백은 한 글자도 바꾸지 않고 log에 옮겨 적는다. 피드백이 곧 다음 판의 측정 목록이다.
8. 자동으로 맞출 수 있는 값(셰이더 상수, 카메라 위치)은 값을 조금씩 바꿔 차이 숫자가 줄어드는 쪽으로 탐색한다. 손으로 덧칠하지 않는다.

산출물
- `out/v1..vN.mp4`, 판마다 나란히 영상, 차이 json, iteration_log.md.

검수 기준
- 보고 전에 원본 해상도로 같은 프레임을 잘라 나란히 본다(확대 크롭 3곳 이상). 접촉표 크기로 "같다"고 하지 않는다.
- 평균 차이가 판마다 줄어든다. 늘었으면 어느 장면이 늘었는지 구간별 숫자로 확인한다.
- 장면별 숫자를 보고에 넣는다. 한 장면만 유독 높으면 그 장면의 장치를 잘못 안 것이다. (모션 쇼릴 첫 판은 전체 5.5인데 유리 구슬 장면만 18.3이었다. 반사 환경을 맞춰 4.89까지 낮췄다.)

자주 틀리는 점
- 눈으로 보고 감으로 만들기. 종이 콜라주 영상은 첫 네 판을 감으로 만들어 전부 퇴짜를 맞았고, 차이 지도를 만든 뒤에야 통과했다. 첫 장면은 아홉 번째 판에서 "지금까지 본 것 중에, 가장 잘 만들었다."를 들었다.
- 모델을 틀리게 세우고 파라미터만 만지기. 액체 글자의 물 덩어리를 넓은 가우시안으로 그렸더니 둥글둥글해졌다. 원본을 한 장씩 재서 「물방울마다 커널을 더한 장」으로 모델을 바꾸고서야 맞았다.
- 숫자만 맞추고 화면이 다르게 보이기. 3D 키보드는 키가 눌리는 깊이와 시간을 원본과 비슷하게 넣었는데도 "입력되는 모션이 없네"를 들었다. 화면에서는 안 보이는 깊이였기 때문이다. 깊이를 두 배 넘게(0.28에서 0.62), 내려가는 시간을 0.05초로 바꿨다. 원본에서 잰 값이 화면에서 읽히는지 마지막에 한 번 더 본다.
- 한 번에 다 고치려 하기. 차이 지도 위에서 제일 큰 곳 하나를 고치고 다시 재는 순서를 지킨다.
- 흔들림을 더해서 "살아 있는 느낌" 내기. 원본에 없는 손떨림은 넣지 않는다. 옛날 느낌은 질감(입자, 망점, 줄무늬)으로 낸다.
- 만들기를 다른 AI에게 통째로 맡기기. 측정과 최적화는 맡겨도 되지만 화면을 결정하는 창작은 직접 하고 몇 컷을 검수한다.

## 4단계. 내 브랜드로 바꾸기

똑같이 만드는 데까지가 공부다. 올릴 때는 바꾼다.

할 일
1. 사용자에게 브랜드 이름, 색(헥스값), 로고 파일, 글꼴, 말투 예문을 받는다. 없으면 물어본다.
2. 움직임을 정하는 숫자(컷 길이, 이징, 간격, 각도, 물리값)는 그대로 둔다. 글·색·로고·사진·소리를 바꾼다.
3. 원본에서 가져온 것을 모두 지운다: 원본 음악, 원본 화면 텍스처, 원본 인물, 원본 로고와 글자. 소리는 새 곡이나 직접 만든 소리로 바꾼다.
4. 내용도 내 것으로 채운다. 내 서비스의 실제 장점, 실제 사진, 실제 화면. 없는 팀·제품·경험을 있는 것처럼 쓰지 않는다.
5. 바꾼 뒤 3단계의 나란히 영상을 다시 만들어 움직임이 유지됐는지(구도·타이밍) 확인한다. 이때 차이 지도의 평균은 올라가는 게 정상이다(글과 색이 달라졌으므로). 장면별 타이밍 프레임이 같은지를 본다.

산출물
- 브랜드판 영상, 바꾼 목록(무엇을 무엇으로).

검수 기준
- 영상 어디에도 원본의 음악·프레임·글자·로고가 남아 있지 않다. 프레임 몇 장을 원본과 대조해 확인한다.
- 처음 보는 사람이 원본을 몰라도 브랜드 영상으로 읽힌다.

자주 틀리는 점
- 원본의 사진 한 장, 효과음 하나를 편해서 남기기. 연습에 쓴 것은 올리지 않는다.
- 색만 바꾸고 글 길이를 맞추지 않아 글자가 상자 밖으로 나가기. 글이 길어지면 틀 안에 들어가도록 크기를 재계산한다.
- 대표자 얼굴 사진을 허락 없이 합성하기. 인물이 필요하면 브랜드가 쓸 수 있는 사진이나 그린 캐릭터를 쓴다.

## 5단계. 스킬로 저장해 계속 쓰기

할 일
1. 장면 코드에서 **바뀌는 것**과 **고정된 것**을 나눈다.
   - 고정: 레이아웃, 타이밍 표, 이징, 물리값, 렌더 명령
   - 바뀌는 것: 글, 색, 로고 경로, 사진 경로, 길이를 정하는 대사
2. 바뀌는 것을 `content.json` 한 파일로 뺀다(`templates/content.example.json` 참고). 코드는 이 파일만 읽는다.
3. 폴더를 `skills/<새-스킬-이름>/` 구조로 정리하고 SKILL.md를 쓴다: 언제 쓰는지, 필요한 입력(content.json 항목), 렌더 명령, 검수 방법, 지키는 선(바꾸지 말 것).
4. 시험으로 content.json의 글과 색만 바꿔 한 번 더 렌더한다. 코드를 건드리지 않고 새 영상이 나오면 완성이다.
5. 다음에는 사용자가 "그 틀로 만들어 줘, 내용은 이거"라고만 하면 스킬을 불러와 content.json만 채운다.

산출물
- 새 스킬 폴더(템플릿 코드 + content 예시 + SKILL.md), 시험 렌더 한 편.

검수 기준
- 새 content.json으로 코드 수정 없이 렌더된다.
- SKILL.md에 "바꾸지 말 것"이 적혀 있다(지적받아 고정한 값, 퇴짜 난 방식).

자주 틀리는 점
- 템플릿 안에 이번 영상의 글이 박혀 있어 다음에 다시 뜯어야 하기. 글자 하나라도 코드에 있으면 content.json으로 뺀다.
- 퇴짜 난 방식을 지우기. 지운 코드는 다음에 또 시도한다. 퇴짜 이유와 함께 "다시 하지 말 것"에 남긴다.

## 보고 형식

사용자에게는 결과만 짧게 보고한다.

- 비교 영상 위치(왼쪽 원본, 오른쪽 재현)
- 장면별 평균 차이 표와 가장 다른 구간(초 단위)
- 남은 차이가 무엇 때문인지 한 줄
- 4단계를 했다면 바꾼 목록

작업 과정 설명("이것을 했습니다")으로 보고를 늘리지 않는다.

## 참고 사례

`prompts/` 폴더에 영상 여섯 편의 실제 지시문, 받은 피드백, 측정 숫자, 작업 순서가 있다. 새 영상을 뜯을 때 가장 닮은 사례를 먼저 읽는다.

- 글자가 녹는 물리 효과: `prompts/liquid-text.md`
- 입자·3D 셰이더 쇼릴: `prompts/motion-showreel.md`
- 사이트 템플릿 카드가 돌아가는 영상: `prompts/template-cube.md`
- 컷이 빠른 브랜드 필름: `prompts/oldfilm.md`
- 종이 오려 붙인 튜토리얼: `prompts/paper-collage.md`
- 2D 카드가 3D 제품으로 바뀌는 영상: `prompts/3d-keyboard.md`

말하는 캐릭터를 만들 때는 `docs/minho-neck.md`를 읽는다.
